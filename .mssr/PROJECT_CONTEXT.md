# MSSR project context

## Architecture

MSSR is the portable deterministic/advisory control layer for routing, bounded skill/project context, trace/lifecycle contracts, consistency evidence, telemetry analysis, and external observe-only learning. Portable MSSR owns schemas plus pure decision/evaluation semantics; Bridge, Codex, OpenCode and other hosts own authorized observation, transport, persistence and I/O. An MSSR evaluation or recommendation never authorizes a mutation.

Project knowledge and procedural context are explicit, bounded evidence. Canonical project truth stays under repository-owned `.mssr/` authorities and ADRs; generated/runtime receipts are reconstructable evidence, not a second authority. Context budgeting uses measured material and must expose omission, deferral, ambiguity or overflow rather than increasing limits or silently truncating required content.

Procedural skill guidance uses stable core/module units and exact paging. R3 Context Economy v2 lets a host attest only units still retained in the current uncompacted context by stable id plus content fingerprint; MSSR suppresses exact matches, re-delivers changed or unretained guidance after compaction/restart/handoff, and binds the attestation set into cursor integrity. Context-delivery depth is now explicitly separate from container authority: an authoritative/required parent guarantees only its core and any child explicitly declared required; optional child material remains accepted and may be omitted under a bounded budget without extending `mustContinue`. The same portable `authority` / `relevant` / `deep` policy can assemble arbitrary authoritative Markdown through adjacent `<document>.context.json` manifests, with core-only delivery before structured intent and host-owned full-document fallback when the manifest is absent or invalid. Detailed retained-context semantics live in `mssr-context-economy-v2`; trace/lifecycle ownership lives in `mssr-trace-lifecycle-integrity`.

Project Context selection, segmentation, health and maintenance are owned by `mssr-project-context-plane-architecture`; Architecture Impact detail is owned by `mssr-architecture-impact-decision`. Deterministic semantic consistency extends the existing Situation Model/C2c/C2d stack: declared owners and typed comparable claims/relations may prove contradictions or explicit unresolved lifecycle targets, while declared/exact/TF-IDF retrieval only finds candidates and never establishes truth, ownership, routing, notice severity or write authority. Only current declared `mirrors`/`summarizes` relations can authorize cross-subject comparison; derived relations and optional model-shadow observations remain candidate-only. `roadmap-contradiction` and `unresolved-reference` are produced from deterministic evidence with stable dedupe and resolution-to-silence. R4 current-truth semantics live in selective module `mssr-semantic-consistency-decision`; relation/retrieval/message/shadow boundaries live in `mssr-semantic-relations-retrieval-decision`. Extractors may read declared machine/checklist/structured fields, never arbitrary surrounding prose. ADR 0006 owns the design.

Semantic Evidence Plane is a staged selective architecture owned by `mssr-semantic-evidence-plane` and ADR 0009. `Document Surface` provides revision-bound section/range metadata; `document-context` is its first migrated production consumer. The advisory `Librarian` catalogs bounded producer identity/source/revision/fingerprints and resolves structural equality deterministically. Semantic Curation has a separate injectable Jev decision-provider contract; Librarian-to-Jev semantic relation triage is still a roadmap item and must not be described as integrated. EvidenceAtom v2 requires source class/canonical owner, exact observation proof for `fresh`, and bounded identifier-like attributes. R5.A owns explicit producer coverage: only tested adapters count as instrumented, and missing/partial families block negative claims for their scope. Required coverage is complete in the current 0.2.91 candidate. Conditional host capabilities use a two-level boundary: a portable MSSR adapter may establish only global `partial` coverage, while actual `instrumented` status requires a separate host-scoped adoption declaration; no host adoption is inferred from portable source alone. Global coverage therefore remains incomplete for host-runtime/filesystem/visual evidence. Explicit verifier evidence is provenance-bound: same-provider or same-trace observations cannot self-confirm semantic truth.

## Project knowledge governance

Project knowledge has explicit owners under the portable `.mssr/` project-control home: `AGENTS.md` is broad repository instruction authority; PROJECT_* remains the compact cross-area control plane; `.mssr/knowledge/<topic>/` owns indexed situational project detail; `.mssr/architecture-impact.json` owns opt-in declared architecture-to-implementation relationships and may name an existing project-context module through `contextRef`; scoped `directive` modules are conditional refinements only; `.mssr/runtime/` is reconstructable delivery state, never authority. Architecture-impact v1 declarations use bounded exact project-relative refs. C2f-B keeps observation ownership split: portable MSSR plans the exact declared refs and validates/normalizes metadata, while each host owns the actual filesystem/runtime read and returns explicit `available`+revision, positively `missing`, or `unavailable` evidence; portable MSSR never synthesizes a successful observation from host failure. C2f-C owns pure reviewed-baseline comparison: explicit reviewed evidence keeps architecture-authority revision separate from the ordered implementation source-set fingerprint and projects only `aligned`, `possible-impact`, or `unresolved`; unavailable evidence never fabricates a change or comparable source-set fingerprint. C2f-C.5-A/B adds optional `.mssr/architecture-structure.json` as a non-widening refinement layer plus pre-edit reverse lookup and sparse Markdown anchor fingerprints, so a touched file can identify all surrounding declared architectures/ADR/context before any hash changes while unrelated document edits can remain structurally irrelevant. C2f-C.5-C supplies host-neutral symbol-analysis/refinement contracts. C2f-C.5-D adds optional `.mssr/architecture-invariants.json` as the explicit repository authority for machine-checkable architecture invariants, while import/call/dependency graph evidence stays `derived`, advisory and non-widening until deliberate promotion to the declared relationship manifest. Bridge-only graph tools may supply observations but are not portable authority. C2f-D (0.2.42) reuses the existing C2e-E exact context-resolution surface at natural MSSR replans: an active Architecture Impact review may recommend only the declared `contextRef` plus architecture authority/ADR, remains advisory and `required=false`, never reruns semantic retrieval, never auto-loads context, never overrides budgets, and emits nothing while architecture is aligned. C2f-E (0.2.43) defines metadata-only reviewed-current receipts for host-local persistence under `.mssr/runtime/`: only an explicit completed review of complete `possible-impact` evidence may create a receipt, and only an exact match of architecture id, declaration fingerprint, reviewed baseline fingerprint, current authority revision, current source-set fingerprint, full projection fingerprint, and receipt integrity may suppress the same repeated review; missing, corrupt, incomplete or changed evidence fails open to REVIEW. Receipts remain reconstructable/advisory and never rewrite canonical architecture. A linked source change can justify review but never proves architecture changed or authorizes a rewrite. MSSR does not read active project-control content from `.bridge/`. Cross-project reusable procedure belongs in an owning skill, where `SKILL.md` is the routed capability core and `references/` are parent-owned situational recipes. Initialization, Project Context Health, `project_change_consistency`, Context Plane freshness, routing audit and structural Skill Health may detect drift and recommend maintenance, but they never silently rewrite an authority; a visible maintenance task reviews evidence and updates the canonical owner.
Document Freshness is a separate opt-in project-knowledge evidence contract. `.mssr/document-freshness.json` may name current-state roadmaps/status/guides plus exact project-relative refs that materially inform them. Hosts own filesystem/Git observation and report bounded availability/revision-order evidence; portable MSSR owns strict validation and `ok`/`watch`/`review` evaluation. A newer declared ref makes the document review-due only: it does not prove a semantic contradiction, parse prose for truth, authorize persistence, or permit canonical rewrite. Historical documents should remain undeclared.

Architecture decisions live under `docs/decisions/`. A Context Message may reference an ADR, incident, changelog, context/state authority, Git revision, provider observation, or trace receipt, but its summary never replaces the referenced owner.

Routing conditions use ordinary any-match dimensions and may use `allNeeds` only when several capabilities are jointly necessary. A broad artifact such as `document` or an approval request is never proof of an unrelated capability. From 0.2.88, structured routing also reports bounded advisory `nearMatches` when a skill strongly matches the supplied intent but remains blocked by one or two explicit semantic gates. Near-matches never enter `loadOrder`, never bypass host-gating and never mutate intent; they expose only matched dimensions plus missing gate values so a host can validate the evidence and perform at most one structured replan instead of silently losing a likely capability. From 0.2.89, host-gated optional-skill feedback also carries bounded maintenance semantics: a skipped `redundant` decision may name an exact observed `relatedSkillName`, while repeated redundancy or `irrelevant-domain` evidence can produce review-only `skill-overlap` / `skill-domain-mismatch` candidates after a distinct-trace threshold. Legacy redundancy without a named peer remains ambiguous and may expose only bounded co-occurring candidates. These candidates never change scores, `loadOrder`, skills, relations or files; reviewed corrections stay in the versioned routing gates and existing `requires` / `complements` / `excludes` relations, or require an explicit owner-approved structural change.

## Repository checkout authority

The canonical MSSR source checkout is `D:\Dev\mssr`. `C:\Dev\mssr` is a Windows junction to that same checkout and is not an independent clone, branch authority, or second source tree. Temporary Codex worktrees may exist for bounded tasks, but they never become canonical merely by containing local edits; before removing an old worktree or branch, verify active-writer state, Git containment, and whether any substantive material is absent from current `main`.
