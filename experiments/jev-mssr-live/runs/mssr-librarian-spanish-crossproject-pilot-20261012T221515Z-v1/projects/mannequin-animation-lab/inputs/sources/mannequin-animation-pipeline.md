# Animation Authoring Pipeline

## Trigger

Typical future request:

> Using the mannequin, generate a new attack animation.

The pipeline must resolve four things before authoring: motion intent, source mode, root-motion mode, and acceptance criteria.

## 1. Choose the source mode

### A — Modify an existing Action

Use when an existing Quaternius Action has useful mechanics/timing. Examples: `Sword_Attack`, `Walk_Loop`, `Sword_Idle`.

Workflow:

1. inspect source Action and rig;
2. choose key phases;
3. persist/reference source poses;
4. create a separately named candidate Action;
5. modify only the required motion intent;
6. review source vs candidate at key and intermediate frames.

This is the preferred early workflow because changes are measurable and body mechanics start from a known-good source.

### B — Compose from existing poses

Use useful poses from one or more Actions as building blocks without copying a full dense Action. Example: sword idle -> custom anticipation -> existing impact-like pose -> custom recovery.

The pose pack must record where each pose came from and what was inferred/changed.

### C — From `A_TPose` / T-pose

Use when source motion is too constraining or a genuinely new action is desired.

1. create an empty candidate Action;
2. establish start/neutral pose;
3. author major key poses center-out: hips -> spine/chest -> legs/feet -> arms/hands -> fingers/head;
4. set contacts and end-effector intent;
5. interpolate;
6. sample intermediate frames;
7. add/reposition poses at the largest observed error until continuity is acceptable.

Do not author every frame manually by default.

## 2. Build the motion reference

A reference pack may start from:

- an existing Blender Action;
- a generated pose-sequence image;
- local video/GIF/reference frames;
- a textual choreography brief;
- a hybrid of these.

Normalize to:

```text
reference-pack/
  manifest.json
  clean/
  technical/
  structured/
    motion-reference.v1.json
  evidence/
```

The structured motion authority for this layer is `MotionReference v1` (`schemas/motion-reference-v1.schema.json`). It is intentionally rig-independent: use semantic joints/contacts such as `hips`, `right.hand` and `left.foot`; concrete Quaternius names such as `DEF-forearm.R` live in `RigAdapter v1`, while action-specific source priors and composition policy live separately in `RigRecipe v1`.

A deterministic technical sheet can be produced with `tools/motion_reference.py`; see `docs/MOTION_REFERENCE_V1.md` and the checked-in `horizontal-strike` example/golden SVG. The first executable rig bridge is documented in `docs/RIG_ADAPTER_V1.md` and resolves `MotionReference + RigAdapter + RigRecipe -> rig-plan -> separate Blender candidate Action`.

The pack should identify named phases such as `ready`, `anticipation`, `load`, `swing`, `impact`, `follow_through`, `recovery` rather than only arbitrary frame numbers.

## 3. Extract machine-readable clues

Use the cheapest reliable source first.

When structured Blender pose data exists, use it directly. For image-only references, possible evidence layers are:

- human pose landmarks;
- segmentation mask;
- silhouette contour;
- centroid / body mass proxy;
- shoulder/hips facing axes;
- limb segment directions;
- feet/hands contact locations;
- weapon trajectory or hand trajectory;
- 2D joint confidence;
- view/camera metadata.

Candidate external primitives include MediaPipe Pose Landmarker for image/world pose landmarks and masks, plus OpenCV contours/moments for silhouette, centroid and geometric measurements. Because the mannequin is stylized, these are helpers, not guaranteed truth.

## 4. Exploit control of image generation

When the reference is generated by us, make it easier to analyze:

- ask for a consistent mannequin-like actor;
- fixed camera and framing;
- clean background;
- full body visible;
- separate side/front/three-quarter views;
- no motion blur or occluding effects;
- clear feet and hands;
- one movement phase per cell;
- generate a **clean** sheet first.

Then create technical layers deterministically when possible. Do not rely on the image model to draw exact bone labels or perfectly consistent marker colors. A post-process can add detected joints, IDs, axes and contacts to produce `technical` evidence while preserving the untouched clean source.

## 5. Resolve 2D to rig intent

A single image cannot uniquely determine 3D depth. The solver should classify each joint as:

- constrained by multiple views;
- constrained by known body proportions;
- inferred with moderate confidence;
- ambiguous/occluded.

For ambiguous poses, prefer requesting/using a side or three-quarter view rather than pretending exact Z coordinates are known.

Map visual joints to semantic roles first, then to real bones:

```text
image right elbow
  -> semantic right.elbow
  -> Quaternius chain DEF-upper_arm.R / DEF-forearm.R
```

Use IK/end-effector goals and bend-plane targets where they describe intent better than direct Euler/quaternion guessing.

## 6. Author the candidate in Blender

Current useful primitives come specifically from **Mauro Blender MCP standalone** (`D:\Dev\blender-mcp`, add-on `mauro_blender_mcp`, default port `9878`, stdio MCP server): pose sampling, candidate Actions, explicit pose keying, bounded F-Curve editing, IK, hand orientation, finger pose/grip, foot locking and fixed-camera animation review. Do not silently substitute the legacy Bridge Blender integration (`D:\Dev\bridge-mcp`, `mauro_blender_bridge`, port `9877`) or a temporary/test instance on another port. This catalog is provisional because the standalone MCP is still under construction; inspect it at execution time.

Author non-destructively:

- source Action stays unchanged;
- candidate gets explicit lineage/provenance;
- key only the intended transforms;
- persist checkpoints/evidence by run;
- do not promote automatically.

## 7. Review trajectories, not only poses

Every major pose can look correct while the movement between them is wrong.

Review:

- adjacent and midpoint frames;
- hand/weapon arcs;
- hips/chest timing offset;
- foot slide and contact;
- knee/elbow bend direction;
- root displacement;
- loop seam when applicable;
- mesh intersections and silhouette pops.

If the largest error falls between two key poses, add or move a key pose there. This is the preferred adaptive simplification loop.

## 8. Accept mannequin motion

Acceptance requires the requested visual intent plus bounded structural/runtime defects. Save:

- candidate Action identity;
- source lineage;
- reference pack;
- key-pose manifest;
- review images/manifests;
- measured defects;
- accepted limitations.

## 9. Retarget / export

Only after the mannequin motion is accepted:

1. map source semantic rig to target semantic rig;
2. normalize rest-pose/axes/scale;
3. transfer trajectories/contacts rather than blindly copying rotations;
4. solve target limbs and bake;
5. repeat fixed-view/contact QA;
6. export and test the real imported animation in Godot or the owning game.

The same accepted mannequin motion can then become a reusable motion asset across multiple games/characters.
