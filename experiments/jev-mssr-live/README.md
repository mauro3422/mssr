# Jev and Librarian live experiments

These runs exercise the local Bridge release adapter against exact frozen MSSR
Markdown. They are exploratory diagnostics, not production rollout or
confidence-calibration evidence.

## Evidence handling

- Keep each run directory immutable after provider calls. Preserve `manifest.json`,
  raw `records.jsonl`, `request-events.jsonl`, and `run-completion.json` as the
  original evidence packet. Correct metadata through a separate append-only
  erratum; never rewrite the frozen manifest or provider records.
- Run a live request only through a frozen runner with explicit `--allow-network`
  and recorded user authorization. Labels stay out of provider requests.
- Run `node experiments/jev-mssr-live/summarize-run.mjs <run-directory> --write`
  after execution. This validates manifest/completion/case/record identities
  and derives request counts, unique source-document clusters, exact fetches,
  evidence packs, tokens, and timestamp warnings from the frozen artifacts.
- Preserve MSSR's returned `evidenceSufficiency` field in each record; do not
  assume that `noul` or `sufficiency` are its schema aliases. The summarizer
  reports missing values as a recording gap, not a provider abstention. Keep
  this score descriptive and uncalibrated.
- For new live packets, copy runner-template.mjs, selection-record.mjs, and
  runner-support.mjs into the run directory before freezing it. Copy
  `config/project-context/project-context-manifest.schema.json` to
  `inputs/project-context-manifest.schema.json`. Record the runner hashes as
  `manifest.instrument.runnerSha256`,
  `manifest.instrument.selectionRecordSha256`, and
  `manifest.instrument.runnerSupportSha256`; run the template without
  `--allow-network` before any provider call. Run
  `npm run fingerprint:jev-live-build -- <Bridge code root>` and copy its
  `instrument.projectContextManifestSchemaSha256` into the packet manifest,
  along with `source.mssrVersion`, `source.mssrPackagePath`, and
  `source.mssrPackageTreeSha256`. Merge its two `source.buildArtifacts` entries
  into the packet's existing list. This fingerprints the installed MSSR tree
  that the imported Bridge tool actually resolves, including generated package
  files; a tarball digest or `package.json` digest alone does not prove those
  installed bytes match. The shared serializer keeps
  canonical evidenceSufficiency separate from a separately returned raw
  noul field. The support module validates one-to-one case/label IDs, exact
  label-to-source bindings, selected-range offsets and byte-for-byte text
  against the normalized frozen source snapshot, range-kind-specific fetch
  fingerprints (sections hash trimmed text; indexed blocks hash their exact
  slice, with normal block offsets already trimmed and list-item indentation
  preserved), evidence-pack citations, and exclusive run locking. Snapshot
  comparison is the primary exact-fetch check; a matching digest alone is not
  treated as proof that returned text came from the frozen source range.
- The reusable runner defaults to `runtime.metadataMode: "off"`; an individual
  frozen case may override it with `metadataMode` and an exact scalar `metadata`
  filter (string, finite number, or boolean). Supported modes are `off`,
  `project-context-single-section`, and
  `project-context-librarian-sidecar`. Any non-off Project Context metadata
  packet must freeze all four controls in `corpus.metadataControlFiles`: the base
  manifest and Librarian sidecar, plus explicit `present`/`absent` states for
  segments and refs. Present controls need exact SHA-256 values and byte-for-byte
  snapshots under `inputs/metadata/`; absent controls use `sha256: null` and
  `snapshotPath: null`. The runner checks these against the live project before
  and after execution, includes metadata mode/filter in each request fingerprint,
  and preserves returned `metadataProjectionMatches` in search records. A zero
  projection-match count is recorded as such; it is not evidence that metadata
  helped. Source refs remain explicit and host-owned—this does not add crawling
  or automatic source discovery. Historical packets and their copied runners
  are not rewritten.
- Every new runner invocation, including metadata-off dry runs, now requires a
  parseable canonical `.mssr/project-context.json` v1 envelope before any Jev
  request. The preflight validates every entry against the repository-owned
  JSON Schema and rejects duplicate IDs across `core` and `modules`. Freeze
  that schema's SHA-256 in the packet manifest. The runner records the manifest
  SHA in the dry-run, request fingerprint, request-start event and completion
  summary, then rechecks it before and after every tool call and at run close.
  A change aborts the run rather than attributing results to a stale manifest
  revision. This gate prevents invalid project initialization or mixed context
  revisions from being misreported as a Jev result.
- Scoring keeps precise `acceptableRanges` separate from optional broader
  `relevantRanges`. An exact-range match is reported independently; a broader
  source section can count as a relevant answer only when its exact lines were
  labeled in advance. This prevents broad retrieval from inflating exact-range
  scores while still measuring whether it returned useful context.
- Labels may optionally declare `answerability: "answerable" | "unanswerable"`.
  Missing `answerability` keeps the historical positive-label behavior. An
  `unanswerable` label must be explicit and must not carry a target heading or
  accepted or relevant ranges; its scope is the case's declared `sourceRef`, not every
  document in the repository. The scorer reports relevant answerable decisions,
  exact-range selections, broader relevant selections, correct abstentions, false selections, and failed/unknown decisions
  separately. A provider/tool failure is never counted as a correct abstention.
  These labels are scorer-only and are not sent to Jev. Captured `choice: "none"`
  is treated as abstention only when the normalized status is absent; the
  canonical `status: "failed"` remains a failure. Contradictory status/choice/
  selected payloads are left failed/unknown instead of being scored as
  abstentions. The added diagnostics do not
  change historical frozen packets and do not make a confidence-calibration or
  semantic-completeness claim.
- `run-completion.json` distinguishes explicit network authorization from
  returned Jev request IDs. The local runner cannot observe transport calls
  below the Bridge adapter, so `providerTransportInvocationsObserved` stays
  `null`; do not interpret the `--allow-network` flag as proof that a network
  request occurred.
- A runner lock left behind after process termination is a recovery signal.
  Inspect the recorded PID and preserve the packet and all partial outputs;
  do not delete or reuse them automatically. For another attempt, freeze a
  new run directory and run ID so the interrupted evidence remains available.
- A runner-produced `summary.json` is convenient output, not an authority for
  cluster counts or semantic answer quality. Copied runners can retain static
  template text. Use `summary-calculated.json` for mechanical counts and keep
  semantic judgments in a separate reviewed file.
- A blind model-assisted review is useful evidence, but it is not owner-gold.
  Keep reviewer identity, input boundaries, and limitations explicit. Do not
  tune confidence thresholds from raw Jev Choice/Noul scores.
- Group queries by source-document cluster. Linked follow-ups, query variants,
  and repeated prompts against the same source are diagnostic repeats, not
  independent benchmark units. Do not pool them as additional holdout samples.
- Record the timestamp at freeze in UTC. Use request-event timestamps as the
  actual execution interval; if a frozen timestamp is wrong, add an erratum and
  preserve the original manifest hash.

## Composed-runner prototype

[`scripts/run-composed-librarian-experiment.mjs`](../../scripts/run-composed-librarian-experiment.mjs) is a development harness for dry-run and provider-off receipt replay. Replay requires a strict receipt linking Jev's recorded choice, offered candidates, and an exact source fetch; it snapshots plan, runner, source bytes, MSSR build identity, and checksums. Its coverage value is explicitly line-span overlap only, not semantic support or owner-gold. Junction/reparse-point paths are refused. Live mode currently writes a checksummed `blocked` record with zero provider/network calls: the local Bridge tree is dirty and the harness cannot prove that its module build is the connected process/catalog. Do not use this prototype to make benchmark, reliability, or confidence-calibration claims.

Together these latest runs show that host-supplied query variants help when wording has low lexical overlap, while adding them to an already-overlapping query need not change the result. Exact retrieval integrity does not ensure complete or focused answers: measure facet coverage and overbreadth separately, and keep the no-candidate abstention distinct from a Jev selection error. Both source clusters in the four-call comparison were exposed to local artifacts; the low-overlap pair is one cluster and not an independent benchmark sample. No confidence threshold or production policy is changed.
