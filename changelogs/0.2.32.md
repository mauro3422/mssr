Native/CLI-style consumers may call the portable helper directly, while Codex/OpenCode inherit the same boundary through `MssrAdapter`; host receipts remain opaque delivery metadata and MSSR adds no queue, retry policy, scheduler, UI, action execution, or new MCP tool.

## Changes

- Added `MssrNoticeHostBoundary<Receipt>` and `deliverMssrNoticeV1(...)` as the immediate direct-host handoff contract. The helper validates the portable notice, gives the host its own validated copy, and returns the unchanged semantic notice plus the host-owned opaque receipt.
- `MssrAdapterOptions` now accepts an optional `noticeDelivery` callback; `MssrAdapter.deliverNotice(...)` invokes it explicitly and fails closed when no host boundary is configured.
- Codex and OpenCode inherit the same direct-host delivery API through their existing thin `MssrAdapter` specializations; native/CLI-style hosts can call `deliverMssrNoticeV1(...)` directly without Bridge.
- Delivery callback receipts may carry host-specific stream/call/session/timestamp/attempt metadata, but none of it enters `MssrNotice` semantics.
- Host callback mutation cannot rewrite the semantic payload returned by MSSR because the callback receives a separately validated copy.
- A host transport exception is propagated as a delivery failure. Portable MSSR performs no automatic retry and never reinterprets transport failure as a semantic notice change.
- Added `scripts/test-operational-notice-direct-host.mjs` to prove native, CLI-style, Codex and OpenCode direct-host parity with distinct receipts and identical `MssrNotice` serialization/equality.
- The Gate E4 regression is included in aggregate `npm test`.
- Gate D `mssr_operational_notice_evaluate` remains evaluation-only and unchanged; Gate E4 adds no new MCP tool, so the standalone MSSR MCP catalog remains 17 tools.
- Bridge Gate E3 is a separate live host adoption: Bridge `0.6.106` packages MSSR `0.2.31`. This 0.2.32 source release does not imply Bridge adoption of E4.
