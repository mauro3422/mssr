# 0.2.63 — 2026-09-16

- Summary: parent-internal semantic segmentation for bounded historical Project Context without changing parent routing identity.
- Areas: project-context, context-economy, semantic-segmentation, maintenance
- PROJECT_CONTEXT: updated
- PROJECT_MEMORY: updated
- PROJECT_STATE: updated

Project Context modules may now attach reviewed semantic `segments` through the optional backward-compatible `.mssr/project-context-segments.json` sidecar while remaining one existing logical module in `.mssr/project-context.json`. Exactly one unconditional baseline is required; optional segments declare exact Markdown headings plus structured selectors and/or bounded summary terms. Parent id, kind, routing selectors, priority and budget remain the routing authority, so segmentation does not create independently ranked child modules. Older MSSR hosts can ignore the sidecar and continue parsing the strict base manifest.

When the parent is selected, MSSR always materializes the baseline and at most one uniquely best optional segment. Matching is deterministic over structured intent plus repository-declared normalized summary terms. Equal top scores do not produce an arbitrary choice: MSSR returns baseline only and exposes `ambiguousSegments` plus per-segment decisions. Declared ranges are validated against the Markdown hierarchy and overlapping segment bytes are rejected.

Project Context Health and write preflight measure segmented modules by the worst payload that can be delivered in one selection (`baseline + largest optional segment`) rather than the size of the complete historical backing file. This keeps physical release history durable while preventing it from consuming context when irrelevant. The selected-payload budget is now explicitly separate from physical backing-file pressure: segmented sources retain the normal 65,536-byte maintenance budget with existing WATCH/REVIEW ratios, while a 262,144-byte recovery hard limit keeps an already-pressured history readable for diagnosis and repair. Growth into either selected-payload REVIEW or physical REVIEW is blocked before persistence; crossing the recovery hard limit is invalid.

The maintenance executor does not invent or rewrite semantic segmentation. Whole-file histories still require reviewed segmentation metadata, and an already segmented module that later exceeds its budget returns `semantic-segment-budget-pressure-requires-review`. Bridge and other hosts remain transport/I/O surfaces; portable MSSR owns selection, validation, ambiguity and budget semantics.

The two existing WATCH histories are migrated without changing their parent ids or selectors. `mssr-architecture-impact-history` now exposes a current cross-host baseline plus targeted coarse/structural and derived-feedback/receipt history; `mssr-context-plane-history` exposes a current persistence-review baseline plus Context Messages/tombstone and host-delivery/cutover history. Representative readback selects roughly 2.0 KB and 1.7 KB respectively instead of each full file, and Project Context Health returns OK without increasing `maxChars`.

Regression coverage includes schema guards, baseline-only fallback, unique deep selection, ambiguity abstention, Markdown overlap rejection, worst-case budget/preflight accounting, explicit segmented-pressure maintenance blockers, and preservation of legacy whole-file/structural-maintenance behavior.

Release verification also makes `dist/.build-receipt.json` deterministic: the packaged finished-build marker no longer embeds wall-clock `builtAt` data. The reader remains compatible with older receipts, while repeated `npm pack` operations over unchanged source can now produce stable package bytes instead of changing solely because `prepare` ran again.
