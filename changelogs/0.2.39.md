## Architecture structural refinement

- Added `src/architecture-structural-contract.ts` and `src/architecture-structural-refinement.ts`, intentionally split after the first combined draft grew to 751 lines so evidence/schema ownership stays separate from baseline/comparison policy.
- Added strict portable evidence for sparse Markdown anchors and reviewed code-symbol selectors. Evidence is bound to exact `sourceRevision`, `fingerprintScheme`, and code `analyzerId` provenance; duplicate or undeclared landmarks fail.
- A structural reviewed baseline requires explicit `reviewed=true`, complete observed landmarks, the same C2f-C coarse baseline identity, the reviewed structure declaration, and source revisions that match the coarse reviewed baseline. It is evidence, not canonical architecture truth.
- C3 compares structural landmarks only for refs that the coarse C2f-C projection already observed as changed. It never suppresses or rewrites that coarse fact.
- Compatible unchanged landmarks refine `possible-impact` to `noise-candidate` / WATCH. A changed reviewed landmark becomes `structural-possible-impact` / REVIEW.
- Structure-declaration change, source-revision mismatch, missing/unavailable landmark evidence, availability transitions, changed refs without declared landmarks, and fingerprint-scheme mismatch stay `unresolved` / REVIEW rather than being guessed equivalent.
- Markdown authority changes outside a selected architecture anchor can be classified as noise candidates, while changes inside the selected anchored section remain review-worthy.
- Added `config/project-context/architecture-structural-refinement.schema.json` with strict host-neutral JSON Schema parity. Delivery metadata such as TTL is rejected from the portable contract.
- MSSR self-hosts C3 sparsely: Architecture Impact Plane now declares the structural contract/refinement/schema refs and only four key code landmarks (`buildArchitectureStructureFingerprint`, `normalizeArchitectureStructuralEvidence`, `createArchitectureStructuralReviewedBaseline`, `evaluateArchitectureStructuralRefinement`).
- C3 emits no Operational Notice, requests no context, persists no receipt, infers no graph relation, and never emits an `architectureChanged` claim. C2f-C.5-D, C2f-D and C2f-E remain separate owners.

## Operational pattern automation policy

- Added `skills/skill-maintenance-loop/references/operational-pattern-automation.md` and indexed it as a selective context module for `repeated-friction`, `manual-workaround`, or `reusable-pattern` signals.
- `skill-maintenance-loop` now treats materially equivalent deterministic sequences as automation candidates only when inputs/outputs, ordering, objective gates, safety boundary, fail-closed behavior, and an existing owner are explicit.
- Preference is to extend an existing owner or add a small deterministic script before inventing another workflow guide or skill. Repetition alone never grants authority.
- Scripts/tools may automate mechanical operations and machine-readable receipts; they must not decide architecture truth, approval, `updated` vs `reviewed-none`, irreversible publication, or other semantic persistence decisions.
- Full artifact digests remain canonical evidence. UI/agent text may use compact aliases such as `pkg:<version>#<8hex>` only as resolvable display references.
- The repeated MSSR release ceremony is the first proving case. A future `release:gate` should collapse verify/package/hash/readback/consistency/trace bookkeeping and prefer one final package after reviewed metadata rather than ceremonial candidate/final double-packs.
- Learning/trace analysis may propose the automation candidate; it may not auto-create, install, or promote the resulting capability.
