## Why this release exists

MSSR `0.2.79` exposed a release-integrity edge case: the same logical Git content could produce byte-distinct npm tarballs when different worktrees materialized text files with different physical LF/CRLF line endings. The package contents normalized to the same text, but the `.tgz` SHA-256 changed, which breaks the invariant that one semantic version should identify one immutable package artifact for host adoption.

`0.2.80` does not rewrite or replace the canonical `0.2.79` artifact. It fixes the packaging path for future releases and assigns the fix a new version.

## Canonical packaging

- `release:gate` still performs the full verification phase before packaging.
- The gate obtains npm's package file list with a dry-run preview, then materializes only that bounded file set into a temporary staging directory through an isolated Git index.
- Git applies the repository `.gitattributes` contract while staging and checking out those files, so text bytes are canonical for packaging regardless of the physical EOL state of the developer worktree.
- The temporary Git index and object directory are isolated from the real repository index. The developer worktree and staged state are not rewritten or renormalized.
- The canonical staging tree also materializes the build-only `src`/`tsconfig.json` inputs and links the already-verified dependency tree so npm's unavoidable `prepare` lifecycle rebuilds `dist` from canonical source bytes. Those support inputs remain outside the public package file set, and the resulting artifact is copied back for independent byte/SHA-256 readback and receipt persistence.

## Regression coverage

The release-gate suite now includes a real npm-pack reproducibility regression. It builds two logically identical package trees whose physical EOLs are deliberately inverted: ordinary text starts once as CRLF and once as LF, while a PowerShell file starts once as LF and once as CRLF. Canonical staging must materialize ordinary text as LF and the PowerShell file as CRLF according to `.gitattributes`, and both variants must produce exactly the same `.tgz` SHA-256.

## Verification and adoption

- Focused `release:gate` automation tests must pass, including the real byte-equivalence regression.
- `npm run verify` and `npm run release:gate` remain the final source/package gates for `0.2.80`.
- Bridge adoption remains a separate consuming-host gate and must bind to the exact `0.2.80` package hash/receipt rather than semver alone.
