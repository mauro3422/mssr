# 0.2.12 - 2026-08-13

## Contract

- Summary: Acknowledged inbox receipts now act as temporary tombstones for identical delivered evidence. `enqueueMssrContextMessages` suppresses a message only when an already-acknowledged receipt carries the same `messageId` and the same stable content fingerprint; any content or revision change (or a different id) reappears, and `receiptRetentionMs` pruning lets the same evidence be delivered again after cleanup. The inbox schema moves to v2 (receipts gain an optional `fingerprint`), and v1 state files migrate transparently on load. Legacy v1 receipts carry no fingerprint and never suppress.
- Areas: context-plane, inbox, context-plane-host, schema, maintenance
- PROJECT_CONTEXT: updated
- PROJECT_MEMORY: updated
- PROJECT_STATE: updated

## Changes

- **Fingerprint identity** (`src/context-message-inbox.ts`): `fingerprintMssrContextMessage` derives a stable sha256 signature over the validated message's advisory content (identity `id` and the `estimatedChars` budget hint excluded), canonicalizing object keys, omitting `undefined`, and sorting arrays so the same bounded evidence hashes identically. Each delivery receipt stores the fingerprint it was selected with; re-selection refreshes it to the current content signature.
- **Tombstone dedupe** (`enqueueMssrContextMessages`): enqueue now builds an acknowledged-receipt tombstone set and skips any message whose `messageId:fingerprint` pair is already acknowledged, reporting it as `deduplicated`. Pending dedupe is unchanged. A message with the same id but changed summary/evidence/revision, or the same content under a different id, no longer matches the tombstone and reappears.
- **Retention cleanup** (`pruneMssrContextInbox`): acknowledged receipts are removed after `receiptRetentionMs` exactly as before; once pruned, the tombstone is gone and identical evidence can be delivered again.
- **Schema v2 + migration** (`MSSR_CONTEXT_INBOX_SCHEMA_VERSION = 2`): receipts gain an optional `fingerprint` (64-hex sha256). `loadMssrContextInboxStateFromFile` upgrades legacy v1 state on load, leaving v1 receipts without a fingerprint (they never suppress, a benign degradation). Malformed or wrong-version state still fails closed.
- **Host surface** (`loadProjectContextHost`/`acknowledgeProjectContextInbox`): no API change; the durable plane now honors the tombstone contract end to end, so a re-route after explicit ack reports the identical message in `inbox.deduplicated` and omits it from `contextMessages.selected` until its content changes or its receipt is pruned.
